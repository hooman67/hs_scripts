# Managed Services

Python + Bazel monorepo for inference services — libraries, workers, pipelines and web APIs contributed by many teams, managed by a central inference platform team.

## System overview

The inference offering has three layers:

1. **Inference Framework** (`pip install frameworks.inference`) — a standalone Python library for defining workers, pipelines, and web apps. Lives in the [ai-platform repo](https://github.com/Adobe-Firefly/ai-platform) under `frameworks/inference/serve/`. Can be used independently of managed services.
2. **Inference Platform** — Bazel build rules, k8s deployment automation (Argo CD), capacity planning. Lives in the ai-platform repo under `platforms/inference/`. Produces the `@platforms_inference` Bazel module consumed here.
3. **Managed Services** (this repo) — the opinionated ecosystem where users contribute service code. Uses the framework for building and the platform for deploying.

Documentation convention:
- `README.md` in this repo is the **public user entry point** (setup, samples, commands).
- `aidoc/` contains **detailed development guides**.
- For the big-picture architecture and deployment paths, see the [Inference Platform docs](https://docs.ai.corp.adobe.com/v3/platforms/inference/aidoc/index.html).

## Boundaries

- `cloud/` contains generated Kubernetes manifests — never edit directly.
- `BUILD` files are auto-generated by gazelle, but some manual edits are expected (e.g. `inference_application(...)`, `data = [...]`, visibility). Run `smake lint` after any change to regenerate and fix formatting.
- Workers must follow the **stub/impl split** — see [Stub vs Impl](#stub-vs-impl-pattern) below.
- Docs URLs: links in this repo use `docs.ai.corp.adobe.com`. That domain is firewalled — **always** replace it with `d225u4m63wjidj.cloudfront.net` before fetching (same site, DNS resolvable everywhere). Local source files under `aidoc/` are also available but may lack rendered diagrams and images.

## Commands

- `smake lint` — auto-fix lint/format, update BUILD files, regenerate lock files. Run after every change.
- `bazel test //services/foo:bar_test` — run affected tests first, then `bazel test //...` for the full suite.
- CI runs `bazel test //...` — passing means the branch is clean (lint, format, types, generated files all included).
- GPU tests: add `tags = ["requires-gpu"]` to the `py_test`. Run locally with `bazel test //services/your/path:your_gpu_test --config=gpu`.
- Docs build is a separate CI check. Keep markdown files out of binary group directories to avoid Sphinx picking them up.

## Common pitfalls

### Shell environment (direnv)

`bazel`, `smake`, and `uv` live under `private/bin/` and are put on PATH by direnv (`.envrc` does `PATH_add private/bin`). Interactive terminals pick this up automatically; the non-interactive shell your tools spawn does **not** — direnv's hook runs via `PROMPT_COMMAND`, which never fires in non-interactive shells, so `cd`-ing in is not enough.

Before invoking any of these binaries, apply the env yourself. Either prefix each command:

```bash
direnv exec /path/to/managed_services -- bazel build //...
```

or, for a multi-command sequence, apply once per shell:

```bash
cd /path/to/managed_services
eval "$(direnv export bash)"
bazel ...
smake ...
```

End users invoking `make`/`smake` from a real terminal already have direnv active — this is an agent-only concern.

### Imports at top of file

Every import goes at the top of the file. No `import X` inside a function body
unless there's a specific, documented reason (e.g. breaking a circular import).
Those rare exceptions must carry a comment explaining why and a
`# noqa: PLC0415` so lint doesn't undo them.

Gazelle depends on this — top-level imports are how it builds the BUILD `deps`
graph. A lazy `import` inside `def execute(...)` on a real runtime dependency
will silently drop that dep from the Docker image, causing `ImportError` in
production.

**Libs consumed only by standalone apps still follow this rule.** If a
lib needs an app-only package that isn't in the monorepo's Bazel env,
design the lib to be generic — take a callable parameter and let the
app inject its bootstrap there.

### Stub vs Impl pattern (Bazel-managed workers only)

Workers living under `services/<team>/<project>/workers/` — i.e. Bazel-managed
workers that rely on gazelle for dep inference — are split into two files:

- `__init__.py` (stub): lightweight. Only imports from `frameworks.inference`, `pydantic`, and
  other worker stubs. Never import heavy deps (torch, diffusers, etc.) here.
- `impl.py`: import **all** real dependencies at the **top level**. This is the entire point of
  the split — gazelle reads top-level imports to auto-generate `BUILD` deps. Lazy imports or
  `# gazelle:ignore` on a real dependency will silently drop it from the Docker image, causing
  an `ImportError` in production.

**Standalone apps do NOT need the stub/impl split** for gazelle purposes. Workers living inside
`services/<team>/<project>/standalone_apps/<app>/` are packaged via the app's
`pyproject.toml` (not gazelle), so there's no dep-inference step that requires
the split. Define the worker as a single class in a single file there.
**Exception:** a stub/impl split is acceptable when top-level imports in the impl would crash
pods running on different hardware (e.g. a CUDA extension crashing CPU pods). Use the
framework's `ImplRef` mechanism and document the reason in the app's `AGENTS.md`.

### Binary manager for model weights

Use `smake binaries add <folder>` to check in model weights. The `.gitignore` file it creates
IS the binary manifest — pass it to `bind()` and the framework downloads weights at startup.
**Always add the manifest as a `data` dep on the worker stub `py_library`** (the one with
`bind()`), not on consumers. This ensures it's in the Docker image. Never add the full binary
group target to `data` — that embeds all weights and bloats the image.
The `binary_group()` rule in `binaries/BUILD` downloads actual weights at build time. **Always
add `tags = ["manual"]`** to it so `bazel build ...` and CI don't trigger downloads. The only
exception is small test-data binary groups where you intentionally want the data present for tests.
See [development guides](./aidoc/development-guides.md#binary-manager-details) for code examples.

### Strict Bazel deps

Every import needs an explicit dep in `BUILD`, even if it is a transitive dep of something already
declared. When adding a new HuggingFace pipeline, expect to need at minimum: `diffusers`,
`transformers`, `sentencepiece`, `accelerate`, `safetensors`, `protobuf`.

### Visibility

Workers and webapps are scaffolded with `//visibility:private`. Change to
`//services/<team>/<project>:__subpackages__` when other targets within your project need to
depend on them (e.g. webapp -> pipeline, dev scripts -> webapp). Never use `//visibility:public`.

### mypy with untyped third-party packages

Add `# type: ignore` at the import line in `impl.py` for packages that have no type stubs.
Do NOT use `tags = ["no-mypy"]` on the impl target — that silences mypy for the entire file.

### Other pitfalls

- **Deploy render failures:** read `<workdir>/log.txt` (path shown in error output) for the real traceback.
- **json_spec is optional:** populated automatically after `smake push-images`; absence doesn't break `smake lint`.
- **Bazel cache:** on compute platform (hostname starts with `pluto-`), add remote cache to `.bazelrc.user` — see [development guides](./aidoc/development-guides.md#build-cache).
