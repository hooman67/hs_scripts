# Foundry allocation audits: use bounded Pluto queries

**Operational lesson (2026-10-09):** The legacy Foundry Pluto MCP's `list_jobs`/`get_filtered_jobs` uses `Page(start=0, count=0, force_all=True)` through vendored `adobe-aip` 10.22. A fleet-wide query returned gRPC `UNAVAILABLE`, `x-envoy-ratelimited: true`, and `retry-after: 1`. This does **not** mean Pluto authentication is broken or that all reads are rate-limited; updating the package is not the demonstrated fix. The official AI Platform plugin's paginated `query_entities` worked earlier. When its query tools were absent from a later session, a bounded, authenticated **read-only** Pluto SDK query also worked. Never go back to an unbounded legacy search to retry an allocation audit.

## Repeatable approach

1. Read the **current** allocation canvas, not prior results. On 2026-10-09 Hooman supplied [canvas F0C7E5KHR6J](https://adobe.enterprise.slack.com/docs/T024FSURM/F0C7E5KHR6J); the default canvas ID in `scripts/find_node_violation.py` is **different**. Use the supplied/current ID explicitly. The read-only `canvas_rows(creds()["slack"]["user_token"], canvas_id)` parser is in that script; never print the token. **Sum all non-struck H200/B200 node amounts within each row**: Qimin's approved cell reads `2 H200 nodes + 16 H200 nodes`, meaning **18 approved**, not 2. On 2026-10-09 both allocation parsers were fixed to sum amounts instead of taking the first integer; check their output against the raw canvas whenever counts look odd. The analyzer uses keyword matching, so manually verify owner, work description, GPU type, rank assignment, and project before calling anything a violation. A job named `layergen_harmonize_smoke` does not prove it is the rejected `Layergen RL` request.
2. Prefer the official AI Platform plugin's `query_entities` with bounded `count` and page `start` when available. For a full Foundry census when that tool is unavailable, use the installed `colligo.pluto` SDK's `PlutoClient` with `CLIContext().select_token_provider()` directly. Avoid `CLIContext().get_client()` if its extra `ping()` is rate-limited. Authenticate normally through the plugin/SDK; never copy tokens into the Git-backed repo.
3. Fetch Foundry projects with `get_projects(client, initiatives=["GAI-415 Foundry"], all=True, return_project_details=False)`. Query `ENTITY_TYPE_JOB` with an OR of `QueryParent(parent_id=p.id)` over those projects, plus `JOB_RUN_COMPUTED_STATE_COMPONENT` and a `QueryValueOfComponent` filter for `JOB_RUN_STATUS_RUNNING` (optionally OR `JOB_RUN_STATUS_RUNNING_UNSTABLE`). Use `SearchEntitiesRequest(query=Query(page=Page(start=start, count=50), rule=rule), component_types=[NAME_COMPONENT, JOB_COMPONENT, JOB_RUN_COMPUTED_STATE_COMPONENT])`; increment `start` by 50 until the returned `total` is covered. A ~1-second pause between pages succeeded. Deduplicate by entity ID and report if `total` moves during pagination; a scan is not an atomic snapshot. Query `PENDING` and `INSUFFICIENT_RESOURCES` separately for waiting demand when relevant.
4. Raw SDK entities have `e.id`, **`e.data.owner`** (not `e.owner`), and `e.data.parent_id`. The previous diagnostic crashed while *printing* `e.owner` after a successful paginated response; that was not a query failure. `ComponentModels.name.get(e).name` gives the job name; `ComponentModels.job.get(e).exec_spec` has `num_ranks` and `host_spec.accelerator_count`/`accelerator_type`. Request only these minimal components and never print complete job specs (they may contain secrets or environment variables).
5. For candidates, fetch `CLUSTER_RUN_REQUEST_COMPONENT` by job ID and count distinct nonempty `r.node_entity_id` across `ranks` to verify **actually assigned** nodes; do not infer physical occupancy solely from configured ranks or `startedAt`. Per-project `p.capacity_usage.quota_usage.xpu_counters["p5en.48xlarge"].quota_used_xpus` is the reserved-fleet H200 occupancy; sum project usage and divide by 8 for **GPU node-equivalents**, not necessarily free schedulable whole nodes. The central `FoundryCompute -- DO NOT USE` project contains `quota_allocated_xpus` for total fleet capacity. Summing job specifications can exceed reserved-fleet usage because jobs can run on other pools. Do not assert "stopping X frees Y reserved nodes" without confirming the pool and node scheduling.
